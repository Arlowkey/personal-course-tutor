# 课程会话流程与交接

本流程服务于用户明确采用的“学习计划 → DayX”学习方式。聊天是同一项目中的独立聊天，不承诺创建单独的系统窗口。当前请求是修改／评估 skill 时不执行以下流程。

## 阶段与确认

| 阶段 | 当前应做什么 | 进入下一阶段的条件 |
|---|---|---|
| 收集资料与条件 | 分析 Sources、定位课程项目，询问缺失的每日时长等 | 足够制定可行计划；用户要求先看草案时明确假设 |
| 计划待确认 | 在“学习计划”聊天展示计划，保存时标待确认 | 用户本人明确采用当前计划 |
| 计划已确认 | 先保存计划、任务与交接起点 | 文件保存成功，且已获创建／打开每日聊天的授权 |
| DayX 等待开始 | 打开每日聊天，介绍今日目标并询问是否开始 | 用户在该日聊天明确说开始／继续，或肯定回答 |
| DayX 学习中 | 按框架、课件顺序、分批教学与反馈 | 用户说当天学习到此为止 |
| 收尾待补充 | 停止教学，询问实际页码／知识点等缺失信息 | 用户给出实际停点，或确认已有记录准确 |
| 整理学习笔记 | 保存真实进度与后续安排后，整理并保存本次个人学习笔记 | 笔记保存成功；不能保存时明确说明并在聊天交付内容 |
| 当天已收尾 | 说明变化、笔记位置和下次起点 | 等用户下一次请求准备／开始 DayN，不自行连开后续聊天 |

确认必须来自人类实际回复；拟好的提示、工具结果、引用的他人文字、沉默和日期变化都不算确认。对当前明确的问题回答“好／可以”可算确认；若同时提出实质修改，先完成修改再确认更新后的计划。用户已明确说开始时不重复询问。

## 一、首次进入课程

1. 用户在课程项目采用本完整流程后，首次只发 `Sources` 文件夹或课程材料也可以开始资料分析，不要求重复写完整长提示。仅上传无明确课程用途的附件时先澄清意图，避免误建课程流程。
2. 通过可用的聊天改名能力，把当前规划聊天命名为 **学习计划**。这只发生在实际初始化／规划聊天，不能把已有 `DayX` 答疑聊天也改成学习计划。
3. 从当前项目／用户指定位置建立资料索引。后续聊天需要使用的课件、试卷与计划应位于同一项目可读位置；附件无法跨聊天访问时先落实共享路径。未获得可读资料与计划时不创建会因缺资料无法开课的新聊天。
4. 检查并询问缺失的考试日期、每日可用时长、当前基础等，按规划指南制定计划。已经提供的信息直接采用。
5. 如用户尚未明确授权自动分聊天，在本次必要的条件询问中一并确认是否由我在计划确认后创建并打开 Day1；用户已明确采用完整流程则不重复请求这项授权。仅要求规划或资料整理不等于授权创建聊天。

新课程可将简短的导师入口合并到项目已有 `AGENTS.md`：课程学习使用 `$personal-course-tutor`，并指向实际计划、任务和进度路径。保留原规则；仅在用户采用完整课程流程的初始化范围内添加，不改全局设置，不写入虚构授权。

## 二、确认计划后创建／复用 Day1

用户确认当前计划后，在允许编辑时先保存为已确认状态，记录 Day1 任务和共享文件位置。保存失败时说明原因，不创建缺少交接资料的聊天。

当环境提供 Codex 聊天管理工具时：

- `set_thread_title` 用于规划聊天命名；`list_projects` 定位当前课程对应的项目，使用返回的真实项目 ID。名称相似但目录不同的项目不混用，无法确定时才询问。
- 创建前查看进度中的聊天映射和必要的项目聊天列表。有本课程本次学习的 `Day1` 就复用，重复确认、重试或再次调用 skill 不应创建多个 Day1。名称相同不是唯一依据，应核对项目、记录的 ID 和学习批次。重复确认同一计划时保留每日聊天当前阶段与真实进度，不把学习中或已收尾的 Day1 重置为等待开始。
- 用户已授权且需要新建时，使用 `create_thread`，title 为 `Day1`，目标为该课程项目，环境默认 local；不创建 worktree，不覆盖用户的模型设置。
- 初始提示明确：使用 `$personal-course-tutor`；给出实际项目目录、计划／任务／进度文件位置、Day 编号；**首次只读取资料、介绍当日范围并问是否开始，等人类答复后授课**。不把完整聊天记录当作唯一交接资料，也不把初始提示写成“立即开始讲解”。
- 创建异步进行：保留返回的标识，按返回状态等待，取得正式 `threadId` 后才使用需要该 ID 的工具；临时 `clientThreadId` 不能代替。结果不明时先查状态，不能反复发起创建。按工具要求检查新聊天状态并保留返回的游标。
- 记录正式聊天 ID、项目和 Day 编号；用户授权打开的聊天通过 `navigate_to_codex_page` 展示。创建成功的回复按应用要求附 `::created-thread{threadId="实际ID"}`（尚在准备时用返回的 clientThreadId）。不要编造标识或在未成功时声称已打开。

若相应工具不可用，保存好资料和交接起点，明确说明需要用户在同项目手动新建／打开 `Day1`，并给一句简短的启动指令。不能只把文字“Day1”当作已经创建聊天。

## 三、开始当天学习

新聊天先读取已确认计划和最新进度，说明今天学什么、课件范围和衔接起点，然后询问“现在开始 DayX 的学习吗？”并结束本次回复等待。人类确认后，按每日授课指南执行：当天整体框架 → 自然模块顺序 → 分批讲解 → 练习反馈。

若该日聊天收到用户直接提出的具体概念／题目，可以先答疑，不把它当作自动确认整天课程已开始。已经处于学习中的连续消息直接接上；用户重新回来明确说继续，也不反复做开始确认。

## 四、当天收尾与后续调整

用户说“Day1 学习到此为止”等时，停止新知识和新题。先利用明确的用户报告和作答整理已知情况；有缺失时用一次简短提问收齐：

- 实际停在什么文件的第几页／什么知识点；一页只学了一半也可按知识点描述。
- 练习实际做到哪道，哪些仍需提示或没弄懂（仅问未明确的部分）。

可以根据聊天提示一个候选位置供确认，但“已经讲到”不等于“用户实际学到”。未收到回答前状态为“收尾待补充”，可以保存已知事实；不能凭最后输出的页码推进进度、标记通过或完成后续重排。用户明确说无法回忆或拒绝补充时保留停点未知，只作清楚标注的暂定调整。

收到停点后：

1. 更新当天真实进度：已讲到、用户确认学到、题目证据、未完成项、尚需复习处和下次起点。结束学习不等于完成全部 DayX 任务；理解与验收分开。
2. 依据剩余日期和时间预算，把未完成的关键内容纳入后续计划，减少重复阅读／选做题，保留必要基础与休息。不能悄悄推迟考试日或增加每日时长；若目标与预算已不相容，说明取舍并询问需要用户决定的调整。
3. 在同一份计划、任务和进度文件中保存更新，保留既有历史与题号。
4. **整理 DayX 我的学习笔记**：接着按照 [笔记规则](teaching.md#学习笔记整理)，结合本次学习聊天、用户回答和练习证据，以第一人称整理五个部分并实际保存。此步骤默认属于收尾，不再等待用户重复请求；用户明确暂不整理时尊重其选择。停点仍待确认时保留“收尾待补充”，不要先写成已完成学习的笔记；用户明确无法回忆或单独要求先整理时，只记录已知事实并标出待确认项。
5. 简短告知实际停点、后续哪些安排变了、下次从哪里继续，以及更新的计划、进度和笔记文件。若预算取舍仍待用户决定，笔记可先整理已确认事实，下次起点标明哪些安排暂定。
6. 当天聊天可直接修改共享计划文件，无需给“学习计划”聊天发消息。收尾后等待用户下一次要求准备／进入 DayN，再创建或复用对应聊天并确认开始；不自动设定提醒或连开所有未来聊天。

Day 编号是学习单元，日期另外记录；跨午夜或一天没学完不自动跳号。用户想沿用某个 Day 或改编号时以其明确要求为准。

## 最少的持久交接信息

优先在已有进度文件中维护简短的“课程流程”小节，不额外建立重复的状态系统。至少能查到：当前课程／项目；计划、每日任务、进度与资料索引位置；计划待确认／已确认；完整分聊天流程是否由用户授权；当前 Day 与实际日期；当前阶段；规划聊天和已创建每日聊天的真实 ID（可用时）；实际停点、未完成项与下一步。

字段取值来自用户与工具真实证据，未确认保持未知。新的 Day 聊天每次读取最新文件，不把创建时的旧摘要当成最终进度。只在同一课程项目读写，不把其他项目的同名文件或 Day1 合并进来。
